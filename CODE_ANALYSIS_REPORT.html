한 줄 요약 — ngrok 유사 기능(터널 + 원격 콘솔 + QR)을 3,000줄 미만으로 동작시킨 아이디어와 UX 완성도는 좋으나, 릴리스된 2.1.0 VSIX가 실행 불가 상태이고, 터널 접근 제어가 전무하며, 모든 터널이 하나의 오리진을 공유해 프로덕션 신뢰성 관점에서는 아직 "개인용 프로토타입" 단계입니다.

가장 시급한 3가지

  • 배포 산출물 파손 (P0): .vscodeignore가 src/**를 제외하도록 바뀌었는데, 런타임 코드(tunnelViewProvider.ts)는 여전히 src/webview/template.html을 fs.readFileSync로 읽습니다. 실제 custom-tunnel-2.1.0.vsix 내부를 확인한 결과 extension/src/ 항목이 0개입니다 → 설치 후 사이드바를 열면 예외로 화면이 뜨지 않습니다.
  • 인증 부재 (P0): 터널 URL은 8자리 hex(uuidv4().substring(0,8))뿐이고 서버·클라이언트 어디에도 인증·인가·레이트리밋이 없습니다. ID를 알면(또는 대입하면) 누구나 개발자의 로컬 서버에 직접 접근합니다.
  • 오리진 공유 (P0): 모든 터널이 debug-tool.onrender.com 한 도메인 아래에서 tunnelId 쿠키로 라우팅됩니다. 쿠키·localStorage·SW 스코프가 터널 간 공유되고, 브라우저 하나로 동시에 두 터널을 쓸 수 없으며, 나중에 연 터널이 앞 탭까지 덮어씁니다.

구조적 판단

핵심 병목은 개별 버그가 아니라 세 가지 설계 결정입니다: ① 요청/응답 전체를 메모리에 버퍼링해 JSON+Base64로 WebSocket에 실어 보내는 비스트리밍 프록시, ② 자식 프로세스 stdout을 정규식으로 파싱하는 IPC, ③ 경로가 아닌 쿠키로 터널을 식별하는 라우팅. 이 셋이 성능 상한(30초/대용량 불가), 로그 유실, 터널 간 격리 실패를 각각 만들고 있습니다.

04주요 데이터 흐름 및 인증/인가 구조

A. 터널 시작 흐름

  1. Webview startTunnel() → postMessage{type:"startTunnel", port, useHttps} (main.js:21)
  2. TunnelViewProvider.handleStartTunnel → TunnelManager.startTunnel(port, useHttps)
  3. spawn(process.execPath, [clientPath, port, wsUrl, "https"?]) — VS Code 내장 Node 재사용 (tunnelManager.ts:60)
  4. 클라이언트가 wss://debug-tool.onrender.com에 접속 → 서버가 uuidv4().substring(0,8)로 ID 발급
  5. 클라이언트가 🔑 터널 ID: xxxxxxxx / 📎 터널 URL: https://…를 stdout에 출력
  6. 확장이 stdout을 정규식 /🔑 터널 ID: ([a-f0-9]{8})/로 파싱 → 성공 시 resolve(tunnel), 60초 내 실패 시 kill()
  7. 진행률 이벤트(wakeupProgress 10→30→60→80→95)를 Webview 오버레이에 반영

B. 외부 요청 프록시 흐름

  1. 외부 브라우저가 GET /57725512/foo 접속
  2. 서버가 경로에서 ID 추출 → Set-Cookie: tunnelId (SameSite=None, Secure) → 302 리다이렉트로 /foo (server:209-218)
  3. 재요청 시 쿠키 → (없으면) ?tunnelId → (없으면) Referer 순으로 터널 판별
  4. 서버가 요청 바디를 body += chunk.toString()로 문자열 누적 후 JSON 프레임으로 WS 전송
  5. 클라이언트가 헤더 정리(host/connection/content-length/accept-encoding 제거) 후 axios로 로컬 호출 (timeout 25s)
  6. 확장자·쿼리 기반 Content-Type 보정 → 바이너리·SVG는 Base64, 그 외 UTF-8 문자열
  7. HTML 200 응답이면 </head> 앞에 콘솔 후킹 스크립트 주입 + no-cache 메타 삽입
  8. 보안 헤더(CSP, X-Frame-Options, HSTS) 제거 후 WS로 응답 → 서버가 writeHead+end (30s 타임아웃)

C. 원격 콘솔 로그 흐름

  1. 주입 스크립트가 document.cookie에서 tunnelId 획득 → console.log/warn/error/info 래핑
  2. fetch(POST /log, {tunnelId, level, message})
  3. 서버가 tunnels.get(tunnelId)로 WS 조회 → {type:"log"} 전송
  4. 클라이언트가 🔍 [REMOTE_LOG] {json}을 stdout에 출력 (client:47)
  5. 확장이 stdout 정규식으로 재파싱 → addLog() → 500개 링버퍼 → logAdded 이벤트 → Webview DOM 추가
3번 흐름은 브라우저 → HTTP → WS → stdout → 정규식 → EventEmitter → postMessage → DOM으로 7단계를 거칩니다. 중간의 stdout 텍스트 구간은 타입 안전성이 없고 청크 경계에 취약합니다(P1-3 참조).

05안정성 문제 및 장애 가능성

P0 배포된 VSIX에 Webview 리소스가 없어 확장이 동작하지 않음

.vscodeignore (미커밋 변경) ↔ src/tunnelViewProvider.ts:186-200
원인
.vscodeignore에 src/**가 추가되었으나, _getHtmlForWebview()는 여전히 path.join(extensionUri, "src","webview","template.html")을 fs.readFileSync로 읽고, style.css·main.js도 src/webview에서 asWebviewUri로 참조합니다.
근거
unzip -l custom-tunnel-2.1.0.vsix | grep "extension/src" → 결과 0건. 직전 버전 2.0.0에는 extension/src/webview/main.js가 포함되어 있음(대조 확인).
영향
치명적. 설치 후 사이드바를 여는 순간 ENOENT 예외 → 대시보드 미표시. 기능 전체 사용 불가.
개선
둘 중 하나. ① .vscodeignore에 !src/webview/** 예외 추가(최소 수정), ② 권장: compile 단계에서 webview 자산을 out/webview/로 복사하고 코드 참조 경로를 out 기준으로 변경. 추가로 vsce package 후 필수 파일 존재를 검증하는 스모크 스크립트를 CI에 추가.

P1 터널 클라이언트에 재연결 로직이 없고 연결 종료 시 조용히 종료

custom-tunnel/client/index.js:397-411
원인
ws.on("close") → process.exit(0). 재시도·백오프가 전혀 없습니다. 서버 측에도 ping/pong heartbeat가 없어 죽은 연결을 감지하지 못합니다.
영향
Render 무료 인스턴스 재시작, 네트워크 순단, 프록시 idle timeout 발생 시 터널이 즉시 소멸. 사용자는 공유해 둔 URL이 갑자기 503이 되는 것만 목격합니다. 장시간 세션에서 반복 발생 가능성이 높습니다.
개선
지수 백오프 재연결(최대 N회) + 서버 setInterval ping/pong(30s) + 재연결 시 동일 tunnelId 재사용(?resume=<id>) 지원. 확장 측에는 reconnecting 상태를 UI에 노출.

P1 stdout 정규식 IPC — 청크 분할 시 로그·ID 유실

src/tunnelManager.ts:73-144
원인
tunnelProcess.stdout.on("data")는 줄 단위가 아니라 임의 바이트 청크를 줍니다. output.match(/🔍 \[REMOTE_LOG\] (.+)/)는 청크당 첫 1건만 매칭하고, JSON이 두 청크에 걸치면 파싱 실패합니다. 또한 로그 메시지에 개행이 포함되면 (.+)가 잘려 JSON.parse가 던집니다.
영향
고빈도 로그 상황에서 로그 유실이 정상 동작이 됩니다. 최악의 경우 터널 ID/URL 라인이 쪼개져 60초 타임아웃 후 "터널 시작 실패"로 오인됩니다.
개선
readline.createInterface로 라인 분할 + matchAll로 전건 처리. 근본적으로는 stdio:["ignore","ignore","ignore","ipc"] + process.send()로 구조화 IPC 전환 권장(타입 안전 + 이모지 의존 제거).

P1 allOutput 무한 누적 — 장시간 터널에서 메모리 증가

src/tunnelManager.ts:68, 74-75
원인
allOutput += output이 resolve 이후에도 모든 stdout을 계속 문자열에 누적합니다. 이 변수는 오직 60초 타임아웃 실패 메시지에만 쓰이지만, 클로저가 프로세스 수명 내내 살아 있습니다. allErrors도 동일합니다.
영향
원격 콘솔이 활발한 세션에서 확장 호스트 메모리가 단조 증가. 로그가 많은 앱을 몇 시간 물려두면 수백 MB까지 갈 수 있습니다.
개선
resolved === true가 되면 누적 중단, 또는 최근 N KB만 유지하는 링버퍼로 대체. 함께 60초 setTimeout 핸들도 성공 시 clearTimeout으로 해제(현재 미해제).

P1 WS 연결 종료 시 대기 중이던 HTTP 요청이 30초간 방치

custom-tunnel/server/index.js:152-155, 347-355
원인
ws.on("close")는 tunnels.delete(tunnelId)만 하고, 해당 터널을 기다리던 pendingRequests 항목은 정리하지 않습니다. 또한 res.on("close") 경로에서 clearTimeout이 호출되지 않아 타이머가 남습니다(finish에서만 해제).
영향
터널이 끊긴 직후 접속한 사용자는 즉시 503이 아니라 30초 대기 후 504를 받습니다. 무료 인스턴스에서는 그 사이 이벤트 루프·소켓이 점유되어 체감 장애가 커집니다.
개선
pendingRequests에 tunnelId를 함께 저장하고 close 시 해당 요청들을 503으로 즉시 종료. 타임아웃 핸들도 엔트리에 담아 모든 종료 경로에서 clearTimeout.

P2 응답 헤더를 클라이언트 값 그대로 writeHead — 예외 시 요청이 영구 대기

잘 구현되어 있는 부분

VS Code 내장 Node 재사용 — spawn(process.execPath, …, {ELECTRON_RUN_AS_NODE:"1"})로 사용자 PC에 Node가 없거나 nvm으로 PATH가 꼬여도 동작합니다(tunnelManager.ts:60). 실제 spawn ENOENT 이슈를 겪고 도출한 해법으로 보이며, 배포형 확장에서 매우 실용적인 선택입니다.
사용자 체감을 고려한 진행률 UX — Render 콜드 스타트를 숨기지 않고 10→30→60→80→95% 단계와 경과 시간을 노출하고, 취소 버튼(cancelPendingTunnel)까지 제공합니다. 제약을 UX로 흡수한 좋은 사례입니다.
로그 XSS 방어 — 확장 측 escapeHtml()(provider:171)과 Webview 측 textContent 기반 이스케이프(main.js:540)가 양쪽 모두 적용되어, 원격 콘솔 메시지 경로는 방어되어 있습니다.
리소스 정리 규율 — dispose()에서 pending 프로세스와 활성 터널을 모두 kill하고 리스너를 해제합니다(tunnelManager:301). 확장 비활성화 시 좀비 프로세스가 남지 않습니다.
바이너리 응답 Base64 처리와 SVG 예외 처리 — 이미지·폰트·wasm을 Base64로 왕복시키고 SVG를 별도로 다루는 판단(client:184-212)은 텍스트 전용 프록시에서 흔히 놓치는 부분입니다.
TypeScript strict 모드 + 명확한 도메인 타입 — Tunnel/ConsoleLog 인터페이스가 정의되어 있고 strict:true가 켜져 있습니다. 확장 레이어의 타입 안전성은 양호합니다.
문서화 습관 — ARCHITECTURE / PUBLISHING_GUIDE / ICON_GUIDE / DEPLOY_TEST / RENDER_DEPLOY 등 3,000줄 규모 프로젝트 치고 문서가 충실합니다(일부 내용 갱신은 필요).

12단계별 개선 로드맵

Phase 1 — 지혈

1주 · 목표: "설치하면 동작하고, 켜둬도 위험하지 않다"
  • P0-1 패키징 복구 + VSIX 내용 검증 스크립트
  • Quick Wins 13건 일괄 적용
  • 2.1.1 핫픽스 릴리스 및 CHANGELOG 갱신

완료 기준: 새 VSIX를 클린 환경에 설치 → 터널 생성 → 모바일 접속 → 콘솔 로그 수신까지 성공

Phase 2 — 보안 기반

2~3주 · 목표: "URL을 모른다"에 의존하지 않는다
  • 터널 secret + 서명 토큰 접근 제어, TTL·수동 폐기
  • WS 핸드셰이크 인증, 터널 수 상한
  • 보안 헤더 재작성 정책, /log 인증·제한
  • 로그 마스킹 + 구조화 로거 + /healthz

완료 기준: 토큰 없는 요청은 401, ID 대입 시도가 레이트리밋에 차단됨을 테스트로 증명

Phase 3 — 안정성 & 격리

3~5주 · 목표: "끊겨도 알아서 살아난다"
  • 자동 재연결 + heartbeat + 세션 resume
  • 서브도메인 라우팅 전환(오리진 격리, 리다이렉트·쿠키 제거)
  • 구조화 IPC 전환, pending 요청 생명주기 정리
  • 통합 테스트 스위트 + GitHub Actions CI

완료 기준: 서버 강제 재시작 후 30초 내 동일 URL로 자동 복구, 동시 터널 2개 독립 동작

Phase 4 — 성능 & 확장

6주+ · 목표: "실제 앱을 그대로 태울 수 있다"
  • 스트리밍 청크 프로토콜(Base64 폐기, SSE·대용량 지원)
  • Webview 증분 렌더링 + 가상 스크롤
  • 다중 인스턴스 라우팅, 콜드 스타트 해소
  • 의존성 통합·번들링으로 VSIX 슬림화

완료 기준: 50MB 파일 다운로드·업로드 성공, SSE 스트림 유지, p95 지연 목표 달성

점수 기준 — 100점은 "프로덕션 SaaS로 운영 가능", 70점은 "팀 내부 도구로 신뢰 가능", 50점은 "개인 사용 가능", 30점 이하는 "구조적 결함으로 사용 시 위험". 각 항목은 본문에서 실제 코드로 근거를 제시한 문제만 반영했으며, 추정에 근거한 감점은 하지 않았습니다.

분석 방법 — 저장소 내 모든 소스 파일(TypeScript 4개, Webview 3개, 터널 server/client 2개, 빌드 스크립트)을 전량 읽고, 배포 산출물 custom-tunnel-{2.0.0,2.1.0}.vsix의 내부 구성을 unzip -l로 직접 대조 검증했습니다. 모든 지적 사항에는 파일과 라인 번호를 명시했으며, 실행 시나리오를 재현하지 않고 코드 정적 분석만으로 판단한 항목은 본문에 그 성격을 명시했습니다. 확인되지 않은 추정은 보고서에 포함하지 않았습니다.
